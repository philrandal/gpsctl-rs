# gpsctl Rust port: status and findings (consolidated 2026-11-25)

Rust port of gpsctl (std-only), this repository. The C side is philrandal/gpsctl; the Rust port is level with C release 2.00. (Moved here from the project notes, 2026-11-25.)

## Current state (2026-11-24/25)
- 77 tests pass; `c-golden/compare_cli.py` (C binary built from the C head vs Rust): 112 of 122 scenarios identical (stdout, exit status, frames sent) at default verbosity and at -vv (the -v run was last done with 101 scenarios).
- Ported on 2026-11-25 from the C unreleased changes (master 09b59e3): empty `$*00` line no longer counts as NMEA sync; NAV-PVT fixType 4 counts as a 3D fix; CFG-NAV5 fixedAltVar decoded unsigned; negative `--echo` refused; leftover command-line words refused (`-e 5` is now an error; words after `--` come before the moved ones in picking the first one reported). 11 new comparison scenarios and a unit test for fixType. Not unit-tested: the `$*00` check (the simulator cannot inject a custom NMEA line), though the code mirrors C.
- Brought level with C 1.42 on 2026-11-24: listen-first autobaud (`SyncMethod::Passive`, 1500 ms per rate, one MON-VER confirm, fallback sweep at 921600) and the 0033 poll limit (with `Sim.bytes_written` and tests); NMEA version validation and 4.11 display (text and JSON); decimal range checks; NAV5 bounds (dynamic model 0 or 2..10 with the C warning, fix mode 1..3, minimum elevation -90..90); UTC standard check (0, 3, 5, 6, 7, 8, 9) with EU/NPLI/NICT names; Bike name; `invalid option` wording; verbosity 0 prints the real error; sync method range 1..3; port-open errors use C's strerror text (no "(os error N)"). The shipped config has verbosity 0, which hid two error-text differences until quiet mode started printing errors: the comparison caught them.
- Deliberately not ported: C `--test` (PPS; removed from C). `--reset` is never retried after a hangup (C retries it).
- Not verified on hardware: the listen-first pass and 0033 limit on a real receiver, NMEA-off fallback sweep, UTC 5/8/9; USB hangup recovery is not testable by the owner (no USB adapter), covered by pty unplug/replug tests only, which is accepted. `golden_autobaud.txt` not regenerated from the new C.

## Command line (src/bin/gpsctl.rs, src/cli.rs, src/queries.rs)
**What exists** (`src/bin/gpsctl.rs`, `src/cli.rs`, `src/queries.rs`): a Rust gpsctl with the C program's options (-v, -q, -p, -j, --shared_port, -a, -b, -M, -s, -B, -n, -Q fix/version/satellites/config, --galileo, --satellites, --configure_for_timing, --save_config, -e, --reset, --help/--usage/--version), the same parsing and constraint checks, the same action order, the same verbosity messages, exit status and JSON (cJSON number printing). Port-hangup recovery is part of the action loop: a failed action on a dead port reopens it (up to 5 s) and retries once; `--reset` is never retried. Build: `./build.sh` (see README.md). Extras: `GPSCTL_CONF` (config file) and `GPSCTL_TRACE=1` (byte trace).

**Verified against the real C gpsctl** (`c-golden/compare_cli.py`): 122 scenarios, each run with C and Rust against its own fake receiver; stdout, stderr, exit status and every frame sent are identical in all 101, run at default verbosity, with an extra `-v` and with an extra `-vv` (`EXTRA_ARGS=-vv`). The shipped config has `verbosity = 0`, so the first 76-scenario run hid verbose-only output; a real run on the receiver showed `--save_config -vv` printing no "Saved GPS configuration" line, which led to the `-v`/`-vv` runs and to extra error-path scenarios. `c-golden/compare_hangup.py` kills the receiver mid-run: the recovery output matches except for one OS-level error message (C: "could not retrieve terminal attributes"; Rust: "serial port hung up (device disconnected?)").

**Real M8 (ntp2, /dev/ttyAMA0, gpsd stopped), 2026-11-21, all with the Rust gpsctl:**
- `-vv -a -Q fix`: synchronized at 115200 after 3 failed rates, CFG-PRT confirmed it, 10 satellites, time accuracy 12 ns.
- `-vv -Q config`: all sections as expected (GPS + Galileo, stationary, TP5 1 PPS / 500 ms, NMEA 4.1 with GSA, GSV, RMC, ZDA on).
- `-vv --configure_for_timing`: silent, as C; config unchanged afterwards.
- `-vv --save_config`: accepted (the receiver already matched the config); the missing "Saved GPS configuration" line was then fixed.
- `-vv -n no` then `-vv -n yes`: each printed "Successfully set new configuration to turn NMEA data off/on for GPS UART..."; `-n yes` when already on is silent, as C.
- `-B` (baud change): worked.
- `-s`, `-e` and `--reset`: tested by the owner afterwards and reported as working (output not captured here).
So every option of the Rust command line has now been run on the real receiver. The fixed-altitude variance stays 0.0001 m2 after the timing run: the receiver ignores that field under mask 0x05F7 (2D fixes only), so the 1 -> 0 difference in the CFG-NAV5 write is harmless.

**Bugs found by the comparison** (all fixed in Rust): JSON numbers used a stricter "does 15 digits read back" test than cJSON's compare_double(), so 0.7 printed as 0.70000000000000007; baud-change, NMEA-on/off and autobaud progress messages at -v/-vv were missing; autobaud did not close the port on failure, so C's recovery reopen did not happen; library error wording for poll timeouts and "body size: N bytes" errors differed from C at -vv; "Saved GPS configuration" and the "failed to save GPS configuration" error layer were missing.

**C behaviour worth knowing:** `-e 1` (separate argument) does NOT give the echo 1 second: an optional argument must be attached (`-e1`, `--echo=1`), so `-e 1` echoes forever and `1` is a stray argument.

**Not done:** a real USB adapter (hangup recovery; accepted, not testable by the owner). The C `--test` option (PPS pin timing via wiringPi) is disabled in C master (commented out: wiringPi is deprecated), so there is nothing to port; the Rust port deliberately has no `--test`. Use `ppstest /dev/pps0` or chrony/ntpd sources to check PPS.


## Library and verification detail
Receiver used for the real-hardware checks: u-blox M8, protocol 18 (ROM CORE 3.01, FWVER SPG 3.01), on /dev/ttyAMA0 at 115200 (Raspberry Pi "ntp2", also runs gpsd/ntpd, stopped during the tests).

## Verified
- **CFG-NAV5 via `ublox` 0.10.0** (default features = std + ubx_proto23) produces byte-identical frames to gpsctl's C code on 10 golden cases (incl. 1.15 m, -1.15 m, -0.005 m, DOP 2.3, 99.95, static hold 5/7/255, BeiDou UTC). The crate scales with `x * (1/scale)` then `.round()` (half away from zero), same as gpsctl's `scaleRound`, so it does not have the truncation bug. Round-trip sweeps (every cm in +-50 m, every DOP tenth 0..99.9, every static-hold 0..255) pass.
- **CFG-NMEA, hand-written** (`src/cfg_nmea.rs`): poll frame, read-modify-write of byte 1 only (echoes all other bytes, 4/12/20-byte bodies), skip-if-already-set, short-body error, config-value -> version-byte conversion (26 golden cases), UBX frame extractor with NMEA-noise resync.
- **MON-VER** (`mon_ver.rs`): 30-byte software, 10-byte hardware, 30-byte extensions, cut at first NUL; 8 golden cases. Real M8: ROM CORE 3.01 (107888), hardware 00080000, PROTVER=18.00, GPS;GLO;GAL;BDS.
- **CFG-GNSS** (`cfg_gnss.rs`): golden from the REAL `ubxConfigSatellites()` against a fake receiver on a pty (14 cases). Real M8: 32 channels, 7 blocks; GPS (8/16) and Galileo (4/8) on, everything else off.
- **CFG-MSG** (`cfg_msg.rs`): UART1 rate = rates[1] (the second of the six rate bytes); enabling/disabling changes ONLY that byte of the polled 8-byte body (other ports keep their rates, trailing bytes echoed); nothing sent when already right; bodies < 4 (query) / < 8 (set) are errors. 12 real-C cases. Real M8: GSA/GSV/RMC/ZDA on for UART1; GGA/GLL/VTG/GRS/GST off for UART1 (GGA/GLL/VTG on for I2C/USB/SPI only).
- **CFG-PRT** (`cfg_prt.rs`): baud at offset 8 (needs 20 bytes), NMEA-out = bit 1 of outProtoMask (offset 14). `change_baud()` ports the current ubxChangeBaudRate (poll old rate, up to 3 tries; no-op if already at the rate; up to 2 attempts, each: poll, send, move host, swallow the ACK for only 250 ms, ask up to twice for confirmation, on failure put host back; after both fail, probe at the old rate then the new, so a change that took but lost its replies still succeeds; otherwise "it is at N" / "it answers at neither X nor Y") behind a `Link` trait; `change_baud_say` also reports C's verbosity messages. Identical frames AND host-baud sequence to the real C run on 5 golden cases (incl. already-at-rate); the "replies lost" and "answers at neither" paths are covered by scripted-Link unit tests only. Real M8: round trips 115200 <-> 230400 worked with both `nmea_tool` and the Rust `gpsctl -B`.
- **CFG-RATE** (`cfg_rate.rs`): measRate, navRate, timeRef; < 6 bytes is an error. Golden from the real `ubxGetConfig()`. Real M8: 1000 ms, 1, GPS.
- **NAV-PVT** (`nav_pvt.rs`): 92-byte check, fields, and `correct_time()` incl. borrows through minute/hour/day/month/year, leap February, invalid date, time not valid. 17 golden cases.
- **NAV-SAT** (`nav_sat.rs`): 8-byte header + 12 bytes/satellite, count clamped to the body, quality/orbit clamp to 5, health raw 2 bits; 8 golden cases.
- **Serial layer** (`serial.rs`, `ubx_io.rs`, `sync.rs`; tests use `sim.rs`, a simulated receiver with a virtual clock): `Transport` trait; `SttyPort` is std-only (stty for line settings, `tcflush`/`tcdrain`/`tcgetattr`/`poll` from the libc std links; one fd for read+write; `min 0 time 1`). `Ubx<T>` = receive/ack_wait/send_acked/poll and `impl Link` so `change_baud` works over any transport. Golden: real `pollUbx` fed 20 byte streams and real `autoBaudRate` with the real synchronizers against a pty receiver that only answers at its own baud (7 cases). Time budgets match the C integer arithmetic, including the baud-scaled poll/ACK allowance (`Ubx::backlog`, 1024 characters at the port rate). `Traced<T>` (`--trace`, or GPSCTL_TRACE=1 for `gpsctl`) logs every byte sent/received with timestamps. 77 tests in all.
- **Port hangup** (`serial.rs`, `ubx_io.rs`, `commands.rs`, `cli.rs`): `Transport::hung_up()` (poll() with no events for POLLERR/POLLHUP/POLLNVAL, plus `tcgetattr` must succeed; same four answers as the real C `portHungUp`) and `reopen(wait, look)`. A zero-byte read is checked with `hung_up()` (with `min 0 time 1` it is otherwise ambiguous), and read/write/tcdrain/tcflush failing with EIO/EPIPE/ENODEV give C's text "serial port hung up (device disconnected?)" at once. `commands::with_recovery` and the CLI's `recover()` = actionRecover: reopen (up to 5 s, every 200 ms; the new descriptor must pass the hangup test too) and run the action once more; other failures pass through. The CLI, like C, closes the port when autobaud fails, so recovery reopens it. `--reset` is never retried (a cold start can make the device vanish; C retries it). Tests on real pty pairs, mock-transport tests, an end-to-end run against a pty that is unplugged mid-command and returns, and a C-vs-Rust comparison (`c-golden/compare_hangup.py`; only one OS-level message differs). Mutations: 5 of 7 caught (survivors not testable). Not verified on a real USB adapter. Linux discards what was still queued in a pty when the far end closes.
- A stray `B5 62` followed by a length over 4096 is treated as noise at once, in both Rust and (since patch 0025) C; length 4096 is still a frame, 4097 is noise.
- **Config** (`config.rs`): ini reader (`;`/`#` end a value, as iniparser) with the C getters' strict rules: yes/no by first character with a warning on unrecognised text, whole-number integers (strtol base 0) with range check, strict finite decimals; bad values give the default plus a warning. The shipped gpsctl.conf passes through the TP5 and NAV5 setters with no warnings. `cfg_cfg.rs` (CFG-CFG save mask 0x041B / device mask 0x17; CFG-RST cold start), `cfg_tp5.rs`, `cfg_nav5_cfg.rs` (read-modify-write that keeps the receiver's other bytes).
- **Command layer** (`commands.rs`): the poll-and-send sequence of each C command over any `Transport`. Golden (`golden_cmd.txt`, 53 cases from the real C functions): ok/error, warning count and every frame sent, in order, all identical; 13 of 14 mutations caught. Real M8 `timing --yes --trace`: ran clean; GNSS and TP5 sets identical to the polled bodies (the receiver prints "Resetting GNSS" after any CFG-GNSS set, even an unchanged one), NAV5 differed only in fixedAltVar 1 -> 0 (C writes the configured value, default 0, every run; the receiver ignores it under mask 0x05F7, it only matters for 2D fixes; a later config query still shows 0.0001 m2), all nine NMEA polls answered, no CFG-MSG sets needed.
- **Command line** (`cli.rs`, `queries.rs`): same option table, parser (slOptions rules), constraints, action order, verbosity messages, exit status, JSON (cJSON's 15-then-17 digit number printing with compare_double tolerance) and port-hangup recovery as the C program; `ubxGetConfig`'s aggregate query is `queries::get_config`. `c-golden/compare_cli.py <c gpsctl> <rust gpsctl>` runs both against fresh fake receivers: 122 scenarios, stdout, stderr, exit status and every frame set identical, at default verbosity, with `-v` and with `-vv` (`EXTRA_ARGS`). Found and fixed by the comparison: cJSON number tolerance, missing baud-change / NMEA / autobaud / "Saved GPS configuration" messages, autobaud not closing the port on failure, library error wording ("timed out while waiting to receive UBX message / Problem receiving poll response", "body size: N bytes"). The first 76-scenario run hid the missing save message because the shipped config has verbosity 0; a real run with `-vv` on the receiver found it.
- `nmea_tool` (older diagnostic tool, same library): `poll`, `set`, `ver`, `gnss`, `msgs`, `prt`, `rate`, `fix`, `sats`, `autobaud`, `baud <rate> [--yes]`, and (with `--yes`, `--config FILE`) `save`, `reset`, `sat`, `tp`, `nav`, `timing`, `nmeadata`, `msg`, `nmeaver`; flags `--force`, `--trace`.

## Hardware lessons (found on the real receiver)
- **Never run with another program on the port.** A running gpsd answered the synchronizer's MON-VER polls itself (and re-set the shared tty speed), so autobaud reported a false "synchronized at 460800" while the receiver was at 115200. With gpsd stopped, autobaud correctly found 115200. `SttyPort::open` and `gpsctl` refuse a port another process holds (scan of /proc/*/fd; needs root to see other users), naming the process; `--force` / `--shared_port` overrides. C gpsctl does the same since patch 0024.
- A host at twice the receiver's rate sees NMEA as garbage with characteristic bytes (`$` arrives as 0x60, then 0x18/0x86/0x98/0xE0/0x78/0x66...): useful to recognise "wrong rate" in a trace.
- Unexplained, not reproduced: twice (once at 230400, once at 115200 after an idle night) a first CFG-PRT read failed because the start of the reply was garbled for ~36 ms after the port was opened; later reads were clean. The first read is therefore retried up to 3 times (reads only, never sets). The 2026-11-21 traces show clean first polls.
- An unsaved CFG-PRT change reverts to the saved rate on receiver reset/power cycle, so a failed or forgotten change is recoverable (`autobaud` also finds it). Nothing in these tests was saved with `--save_config` except the one `--save_config` run on 2026-11-21 (the receiver already matched the config).
- The receiver's once-a-second NMEA burst is ~1.2 KB; a poll reply queues behind it. Fine at 115200/230400, but at 9600 baud a burst takes > 1 s. Both implementations add the time to receive 1024 characters at the port's rate to poll/ACK waits (+1.07 s at 9600, +88 ms at 115200). Tested with pty fakes that reply late; not measured on the real M8 at 9600.
- The shipped config files wrote units after numbers ("56 nanoseconds"), which the strict integer reader rejected, silently using defaults (fixed in C patch 0028: units are comments).
- Test hygiene: a pty master opened without O_CLOEXEC is inherited by the `stty` child processes other tests spawn, which keeps it open and made the hangup tests flaky until it was opened with O_CLOEXEC. A comparison run at the shipped config's verbosity (0) hides verbose-only output: run C-vs-Rust comparisons at `-v` and `-vv` too.

## Gaps / gotchas in the `ublox` crate (0.10.0)
- No typed **CFG-NMEA** packet. `cfg_val` only exists on protocol 27+, so a protocol-18 M8 cannot use it. Hand-write CFG-NMEA.
- **Watch dynamic model** (value 9) is only compiled in with feature `ubx_proto27` or later.
- `CfgNav5Params::all()` is **0xFFFF**, not 0x05FF. gpsctl sends 0x05F7; build the mask from named flags.
- Types are under `ublox::cfg_nav5::{CfgNav5Builder, CfgNav5Params, NavDynamicModel, NavFixMode}`; `UtcStandardIdentifier` is at the crate root.
- Builder takes physical units and clamps instead of wrapping (e.g. negative fixed_alt_var -> 0, where C wraps).
- Needs **rustc >= 1.88**.
- No serial layer (hence the hand-written one here).
- The crate has typed CfgMsg, CfgPrt, CfgRate, NavPvt, NavSat; the hand-written versions here were checked against the C code, not against the crate.

## Not yet done / accepted
Decision taken earlier: keep gpsctl's own strict config rules and write our own small ini reader (no `configparser` crate). Still open: hangup recovery has not been tried on a real USB adapter; the tool has no CFG-TP5 / CFG-NAV5 read-back command (the `-Q config` query now shows both); 9600-baud reply lateness not measured on the real M8; cause of the start-up garble unknown; no JSON-schema or serde use (JSON is hand-printed to match cJSON).

## Lessons from the C review that the port should keep
Round, don't truncate, when scaling doubles to integers; echo unknown body bytes when read-modify-writing; validate body sizes before indexing; poll before change and skip no-op writes; open a serial port once for write+read (data is dropped while no fd is open); ctype functions need unsigned char values; never trust an ACK for a baud change, re-poll instead; consume a CFG poll's trailing ACK so it can't be mistaken for a later set's ACK; refuse to share the port with another program; size waits by the line rate, not a fixed second; be strict about config numbers and put units in comments; a zero-length read can mean the port is gone, so check for hangup rather than waiting out the timeout; don't repeat a cold-start reset automatically; compare against the real program at every verbosity, not just the configured one.
